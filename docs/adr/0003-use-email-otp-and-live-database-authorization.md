# Use email OTP and live database authorization

No Excuses will use invitation-gated email one-time passcodes through Supabase Auth and treat PostgreSQL application state—not mutable metadata or cached JWT claims—as the authority for Account, Group membership, Group-admin, peer-decision, operator, and access status. This keeps the private pilot usable for one developer while making immediate revocation, membership-era visibility, operator separation, and cross-Group denial explicit.

## Consequences

- A vendor Auth identity links one-to-one to an app-owned Account. Group memberships are separate time-bounded records; every return creates a new membership. Group-admin assignments attach to memberships, peer authority comes only from the applicable decision's eligibility rules, and operator authority is never a member role.
- The pilot uses six-digit email OTP as its only member sign-in method. Password, phone, anonymous, and Apple or Google sign-in are excluded. Account creation remains invitation-gated: the server validates an application Group invitation before provisioning or enabling an Auth identity, and ordinary OTP requests cannot create unknown users.
- A Group invitation is an application record rather than a Supabase Auth invitation. It is bound to one normalized verified email address, uses a high-entropy opaque value whose digest alone is stored, expires after seven days, is revocable and single-use, and is consumed only by an explicit atomic acceptance command after capacity, one-Group, consent, age, target, and identity checks pass. Link preview or token validation never accepts an invitation.
- Member sessions may coexist across devices. Refresh credentials live only in platform secure storage; the access-token lifetime remains one hour unless measured risk requires a shorter value. Every protected API and media operation checks live Account and membership state, and sensitive revocations use a server-maintained cutoff so an unexpired token cannot preserve access after departure, suspension, deletion, or global sign-out.
- A fresh email OTP is required for verified-contact changes, global sign-out, Account deletion, and sole-member Group closure. A lost verified email does not authorize operator-assisted identity transfer: the operator may suspend and handle a deletion or new-start case under the documented support and privacy process, but never transfers private history based on Group-member testimony.
- The mobile client uses Supabase Auth and narrowly scoped signed media transfers directly but never performs business-table mutations. Versioned API commands verify the JWT and resolve current authority from PostgreSQL. Group IDs, membership, admin status, and operator authority are not trusted from `user_metadata`, `app_metadata`, or custom JWT claims.
- Exposed tables use least-privilege grants plus default-deny RLS, and private Storage policies follow the same boundary. Ordinary server operations preserve caller context. Narrow private-schema `SECURITY DEFINER` functions may perform atomic multi-row transitions only with a pinned empty search path, schema-qualified objects, revoked public execution, an explicit caller check, and focused grants.
- Group-owned records carry an authoritative Group association and, where authorship or historical visibility matters, the originating membership. Current Group state and historical artifacts use different visibility rules: active members may see the defined current snapshot, while detailed history and decision audiences ordinarily use membership intervals or immutable eligibility snapshots. The bounded Wall exception authorizes every current Group member, including a later joiner or return, to see each still-retained Verified item's week and date, author, activity type, structured Workout details, Verified status, photos, and available descriptions; it grants no access to other earlier activity or decision history.
- The Private-pilot operator and developer backup use separate named staff identities, never shared member accounts. Operator access requires TOTP MFA, a live operator assignment, an active case or approved purpose, a named command, and a reason-coded audit record. The operator receives no general Group-browsing, SQL-console, service-key, or peer-accountability authority. Developer infrastructure access is break-glass, separately authenticated, and audited.
- Supabase secret or legacy service-role keys remain server-only and are contained behind a small privileged adapter for Auth administration, deletion orchestration, queued maintenance, and explicitly approved operator commands. A privileged client is never reused as a member-session client, and no bypass-key operation trusts a client-supplied Group, role, Account, or operator assertion.
- Departure, suspension, and Account deletion first create an authoritative access cutoff and complete the required domain cleanup transaction. Account deletion then runs as an idempotent workflow across application data, private Storage, processors, and finally hard deletion of the Auth user; retained finalized history uses Former member and restricted audit evidence contains no reusable identity or credential.
- Pilot readiness requires positive and negative authorization tests across current, pre-join, departed, returned, admin, peer, blocked, operator, developer, service, and stale-session cases; concurrent invitation tests; physical-device OTP and secure-session tests; privileged-key scans; and a deletion rehearsal that includes an outstanding unexpired JWT.
