# Managed backend service options for the private pilot

Research snapshot: 2026-09-01. This note compares documented capabilities and constraints; it does not recommend or rank an option. The baseline is a React Native/Expo iOS-and-Android client, a worldwide private pilot, and the project gates in [Private-pilot technical quality bar](../implementation/private-pilot-technical-quality-bar.md): structured-data RPO at most 15 minutes, core RTO at most four hours, durable Proof before acknowledgement, active and processor deletion within seven days, backup expiry within 30 days with deletion records reapplied after restore, 14-day diagnostics, and 90-day restricted audit evidence.

## Geographic behavior and availability

### Supabase / Postgres

Each project has one primary region, which determines where its primary data is stored; Supabase currently lists specific AWS regions in North America, South America, Europe, Asia, and Oceania. Edge Functions normally execute close to the caller, but database-heavy functions can instead be pinned near the database. Paid read replicas can place read-only copies in other regions; writes and authoritative transactions still return to the primary ([project regions](https://supabase.com/docs/guides/platform/regions), [regional function invocation](https://supabase.com/docs/guides/functions/regional-invocation), [read replicas](https://supabase.com/docs/guides/platform/read-replicas/getting-started)). A worldwide pilot therefore needs measured latency from intended countries and a documented primary-region/data-residency choice.

### Firebase / Google Cloud

Firestore offers many regional locations and three multi-regions (`eur3`, `nam5`, `nam7`). A multi-region stores full replicas in two regions plus a witness and can continue serving after loss of a region; a regional database replicates across zones. The chosen database location cannot be changed in place. The published SLA is 99.999% for multi-region and 99.99% for regional Firestore ([Firestore locations](https://firebase.google.com/docs/firestore/locations)). Other components have their own locations; Firebase documents that Authentication processes data exclusively in the United States, while Firestore, Functions, Storage, App Check, and several other services can have service-specific location behavior ([Firebase privacy and data locations](https://firebase.google.com/support/privacy)).

### Pragmatic AWS-native

AppSync, Cognito, Lambda, DynamoDB, and S3 are regional building blocks available in many regions; a basic stack is still a single-region deployment. DynamoDB Global Tables add managed multi-active, multi-region replication. S3 Multi-Region Access Points add a global endpoint over replicated regional buckets. Cognito multi-region replication is a paid Essentials/Plus capability, is not yet eligible for every user pool, and is eventually consistent; a multi-region AppSync API and compute layer must be separately deployed and routed ([AppSync regions](https://docs.aws.amazon.com/general/latest/gr/appsync.html), [DynamoDB Global Tables](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/GlobalTables.html), [S3 Multi-Region Access Points](https://docs.aws.amazon.com/AmazonS3/latest/userguide/MultiRegionAccessPoints.html), [Cognito multi-region replication](https://docs.aws.amazon.com/cognito/latest/developerguide/user-pool-multi-region.html)).

## Recovery, deletion, and the pilot gates

### Supabase / Postgres

- Paid projects receive daily backups with 7-, 14-, or 30-day plan retention. PITR is a paid add-on with second-level restore selection and 7-, 14-, or 28-day retention, but requires at least Small compute. Daily backup alone does not meet the 15-minute structured-data RPO; PITR is the documented hosted mechanism that could. Restore downtime depends on database size and must be measured against the four-hour RTO ([database backups](https://supabase.com/docs/guides/platform/backups)).
- Database backups contain Storage metadata, not Storage objects. A deleted Storage object is permanently removed and unrecoverable. Proof durability and acknowledgement therefore require a tested object-upload-plus-authoritative-record protocol; a database restore cannot restore lost media ([database backups](https://supabase.com/docs/guides/platform/backups), [delete objects](https://supabase.com/docs/guides/storage/management/delete-objects)).
- Deleting an Auth user does not itself define deletion of application rows and objects; users that own Storage objects cannot be deleted until those objects are handled, and already-issued stateless access tokens remain valid until expiry unless sensitive paths also check session state. The product needs an idempotent, auditable deletion workflow across Storage, application rows, Auth, logs, and downstream copies ([user management](https://supabase.com/docs/guides/auth/managing-user-data)).
- Project backup retention can be kept within 30 days, but a restore can still reintroduce logically deleted structured data. The product's deletion tombstones and restore gate remain required. Storage is not covered by database backup, so any added independent object backup/versioning must also enforce the 30-day deletion clock.

### Firebase / Google Cloud

- Firestore PITR retains versions for seven days at one-minute granularity. Daily/weekly scheduled backups can be retained up to 14 weeks and restore into a new database; exports can be stored longer. Those facilities can support the 15-minute RPO and four-hour RTO only after an isolated rehearsal. To meet the product's deletion gate, scheduled-backup/export retention must be explicitly capped at 30 days and deletion tombstones applied before making a restore accessible ([PITR](https://firebase.google.com/docs/firestore/pitr), [disaster recovery](https://firebase.google.com/docs/firestore/disaster-recovery), [backups](https://firebase.google.com/docs/firestore/backups)).
- Firestore backup does not protect Proof objects. Google Cloud Storage enables seven-day soft delete by default and can add object versioning/lifecycle rules; retained deleted versions remain separate copies until their policies expire. Proof acknowledgement still needs a tested, idempotent protocol across the object write and authoritative Firestore state ([Cloud Storage overview](https://docs.cloud.google.com/storage/docs/introduction), [Object Versioning](https://docs.cloud.google.com/storage/docs/object-versioning)).
- Deleting a Firestore document does not delete subcollections. Firebase's Delete User Data extension can be configured to delete Auth-linked data in Firestore, Realtime Database, and Cloud Storage, but it only deletes explicitly configured paths; recursive mode is required for subcollections. Other Google Cloud or downstream copies remain the application's responsibility ([Firestore deletion](https://firebase.google.com/docs/firestore/manage-data/delete-data), [Delete User Data extension](https://firebase.google.com/docs/extensions/official/delete-user-data)).
- Managed Firestore export writes vendor-specific database export files to Cloud Storage rather than a neutral relational dump, and exports are not exact snapshots at export start. Auth users can be listed/exported, including password hashes with a privileged permission, so identity migration is possible but operationally separate from data and object migration ([Firestore export/import](https://firebase.google.com/docs/firestore/manage-data/export-import), [Auth user export](https://firebase.google.com/docs/auth/admin/manage-users)).

### Pragmatic AWS-native

- DynamoDB PITR supports per-second restore points for 1–35 days and restores to a new table; on-demand backups support longer retention. A 1–30-day setting can fit the pilot's structured-data RPO and backup-expiry gate, subject to an isolated four-hour restore rehearsal and explicit deletion-tombstone replay ([DynamoDB backup and restore](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/Backup-and-Restore.html)).
- S3 needs its own durability/deletion policy. Versioning can preserve deleted objects; lifecycle rules can expire noncurrent versions after a chosen interval. Proof acceptance must be designed so the durable S3 write succeeds before the authoritative record is acknowledged, and all versions, replicas, failed multipart uploads, and downstream copies obey the deletion clock ([S3 access control and versioning](https://docs.aws.amazon.com/AmazonS3/latest/userguide/access-control-overview.html), [S3 lifecycle](https://docs.aws.amazon.com/AmazonS3/latest/userguide/how-to-set-lifecycle-configuration-intro.html)).
- DynamoDB can export full or incremental PITR data to S3 as DynamoDB JSON or Amazon Ion without consuming read capacity. These are parseable formats, but the table keys/indexes and Amplify/AppSync authorization model are AWS-specific and would need transformation for another backend ([DynamoDB export](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/S3DataExport.HowItWorks.html), [export formats](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/S3DataExport.Output.html)).
- Cognito user profiles can be enumerated/exported, but migration remains a distinct workflow. AWS documents bulk import and just-in-time migration triggers; current enhanced user pools can import supported password-hash formats. Deleting a Cognito user has no built-in cascade across DynamoDB, S3, logs, replicas, or exports, so the application needs an orchestrated deletion workflow ([Cognito imports](https://docs.aws.amazon.com/cognito/latest/developerguide/cognito-user-pools-using-import-tool.html), [migration trigger](https://docs.aws.amazon.com/cognito/latest/developerguide/cognito-user-pools-import-using-lambda.html)).

## Observability, audit, and security

### Supabase / Postgres

Supabase exposes Logs Explorer across API, Postgres, Auth, Storage, Realtime, and Functions, and supports external log drains. Published plan retention is one day on Free, seven days on Pro, 28 days on Team, and 90 days on Enterprise; platform audit logs begin on Team ([logging](https://supabase.com/docs/guides/monitoring-and-debugging/logs), [pricing plan comparison](https://supabase.com/pricing)). The 14-day diagnostics and 90-day restricted application-audit gates therefore require either a qualifying tier, a scoped external log drain with its own retention/access controls, or an application audit store. Supabase states that the hosted platform is SOC 2 Type 2 compliant, but customer-side RLS, authorization, secrets, telemetry minimization, and audit design remain project responsibilities ([SOC 2](https://supabase.com/docs/guides/security/soc-2-compliance)).

### Firebase / Google Cloud

Firestore exposes usage, latency, connection, and Security Rules metrics through Firebase/Google Cloud consoles and Cloud Monitoring. Cloud Functions emits structured logs to Cloud Logging with execution IDs; Google Cloud log buckets can be configured for 1–3650 days, allowing separate 14-day diagnostic and 90-day restricted-audit buckets ([Firestore monitoring](https://firebase.google.com/docs/firestore/monitor-usage), [Functions logging](https://firebase.google.com/docs/functions/writing-and-viewing-logs), [Cloud Logging retention](https://docs.cloud.google.com/logging/quotas)). Firebase App Check can reject requests from unattested app instances, but it supplements rather than replaces Auth and Security Rules ([App Check metrics and enforcement](https://firebase.google.com/docs/app-check/monitor-metrics)). Firebase reports ISO 27001 and SOC 1/2/3 evaluations; customer configuration and end-user privacy duties remain shared responsibilities ([Firebase privacy and security](https://firebase.google.com/support/privacy)).

### Pragmatic AWS-native

Lambda sends invocation logs and metrics to CloudWatch; AppSync and other services can also emit CloudWatch logs/metrics, while X-Ray supplies tracing. CloudWatch log groups have configurable retention, so 14-day diagnostic and 90-day application-audit stores are feasible. CloudTrail's built-in event history is an immutable 90-day record of management events, but it does not include data events; S3 object access and equivalent data-plane audit require a trail/event data store or application audit events ([Lambda monitoring](https://docs.aws.amazon.com/lambda/latest/dg/lambda-monitoring.html), [CloudWatch log groups](https://docs.aws.amazon.com/AmazonCloudWatch/latest/logs/Working-with-log-groups-and-streams.html), [CloudTrail history](https://docs.aws.amazon.com/awscloudtrail/latest/userguide/view-cloudtrail-events.html)). IAM, KMS, WAF, S3 Block Public Access, AppSync authorization, and per-service encryption provide building blocks, with configuration owned by the project under AWS's shared-responsibility model ([AWS shared responsibility](https://aws.amazon.com/compliance/shared-responsibility-model/)).

## Pricing transparency and meaningful lock-in

### Supabase / Postgres

Supabase publishes a bundled plan plus per-project compute and explicit usage overages for database size, Storage, egress, Auth MAU, Edge Functions, Realtime, and logs ([billing overview](https://supabase.com/docs/guides/platform/billing-on-supabase), [pricing](https://supabase.com/pricing)). The system of record is standard Postgres with direct connections and `pg_dump`/SQL export, and the stack can be self-hosted. Portability is not zero-cost: managed-to-self-host restore does not cover Storage objects or Edge Function deployment, Supabase-managed schemas and version differences require care, and Auth/OAuth/JWT settings need reconfiguration ([restore to self-hosted](https://supabase.com/docs/guides/self-hosting/restore-from-platform), [self-hosting differences](https://supabase.com/docs/guides/self-hosting)).

### Firebase / Google Cloud

Firebase publishes free quotas and pay-as-you-go unit pricing, with Firestore billed by document/index reads, writes, deletes, stored bytes, backups/PITR, and network transfer; underlying Google Cloud services add separate SKUs ([Firebase pricing](https://firebase.google.com/pricing), [Firestore billing](https://firebase.google.com/docs/firestore/pricing)). Lock-in is concentrated in Firestore's document/query/index and Security Rules model, Firebase client SDK behavior, callable/event triggers, and cross-service identity conventions. Data and users are exportable, but a move to a relational backend requires data-model, query, rule, transaction, offline-sync, and function rewrites rather than only moving files.

### Pragmatic AWS-native

Amplify backend resources have no single bundle price: Cognito, AppSync, DynamoDB, Lambda, S3, CloudWatch, queues/schedules, data transfer, backups, and optional multi-region features are billed separately, mostly pay-as-you-go. AWS publishes per-service prices and a multi-service calculator, making unit costs visible but requiring a workload model to produce a whole-stack estimate ([Amplify pricing](https://aws.amazon.com/amplify/pricing/), [AWS pricing model and calculator](https://aws.amazon.com/pricing/), [DynamoDB pricing](https://aws.amazon.com/dynamodb/pricing/)). Infrastructure is declared through Amplify/CDK and individual resources remain accessible directly, but the default AppSync/DynamoDB access patterns, Amplify-generated schema and authorization, Cognito identities, IAM policies, Lambda triggers, and multi-service operational wiring create meaningful migration work even when exported data is readable.

## Zero-spend staging for Supabase

This staging analysis does not select Supabase; it identifies how long that lane can remain at $0 without treating incomplete infrastructure as readiness evidence.

- **Local development:** `supabase start` runs Postgres, Auth, Storage, Studio, and the other local services in a Docker-compatible runtime. It is suitable for schema, migrations, RLS, Auth/Storage/API flows, tests, and logical dump/restore scripts without a Supabase Cloud charge. Supabase says the local stack must not be exposed publicly. Self-hosting likewise avoids a Supabase subscription, but the team must supply and operate compute, storage, networking, hardening, backups, recovery, uptime, and monitoring; it is not a managed free tier ([local development](https://supabase.com/docs/guides/local-development), [self-hosting](https://supabase.com/docs/guides/self-hosting/docker)).
- **Hosted Free:** $0 includes two active projects, 500 MB database, 1 GB file storage, 50,000 MAU, 500,000 Edge Function invocations, two million Realtime messages, and 5 GB egress. This is enough for disposable physical-device and network integration with synthetic or non-sensitive data, subject to quotas; it is not pilot-readiness infrastructure ([pricing](https://supabase.com/pricing)).

| Approved gate | Why hosted Free cannot establish it |
| --- | --- |
| Structured-data RPO at most 15 minutes | Free has no managed automatic backups or PITR. A scheduled CLI dump can exercise a team-operated path, but it does not prove Supabase-managed recovery. Even the paid daily-backup cadence can lose up to a day; hosted PITR is the documented seconds-granularity mechanism. Database backups also exclude Storage objects ([backups](https://supabase.com/docs/guides/platform/backups)). |
| 14-day diagnostics | Free exposes one day of logs and cannot use log drains. Pro exposes seven days, so Pro alone also misses this gate; a retained external drain or deliberately operated application telemetry store is required ([pricing](https://supabase.com/pricing), [log drains](https://supabase.com/docs/guides/monitoring-and-debugging/log-drains)). |
| Non-pausing availability | A low-activity Free project can pause after seven days. Requests may typically prevent pausing but do not create a guarantee; paid projects are not auto-paused ([Free project pausing](https://supabase.com/docs/guides/platform/free-project-pausing)). |
| Representative restore rehearsal | Free has no managed backup history to restore. A CLI dump/restore proves only that self-managed path. A paid restore makes the project inaccessible and its duration depends on database size, so the actual paid recovery path must still be timed against the four-hour RTO ([backups](https://supabase.com/docs/guides/platform/backups)). |

**Latest payment point.** Coding and ordinary device integration can remain local/Free. For a managed Supabase design, paid infrastructure is required no later than the start of the formal production-like internal readiness rehearsal, before real rehearsal data is admitted—not merely when the live Validation pilot begins. That rehearsal must produce the representative restore, retention, availability, and alerting evidence required before live use. Keep the qualifying configuration through the live pilot and its closeout/retention work.

**Lowest documented managed floor.** Stage daily development locally; use hosted Free only for disposable device-integration checks; then activate one paid project for the formal rehearsal, reset it under the verified runbook, and reuse it for the live pilot. The published full-month equivalent for the hosted RPO/availability floor is about **$130**: Pro $25/month, Small compute $0.0206/hour (about $15/month), less the plan's $10 monthly compute credit, plus seven-day PITR at $0.137/hour (about $100/month). Compute and PITR are hourly/prorated, while the Pro subscription is the fixed plan charge ([compute pricing](https://supabase.com/docs/guides/platform/manage-your-usage/compute), [PITR pricing](https://supabase.com/docs/guides/platform/manage-your-usage/point-in-time-recovery)).

Pro's seven-day logs still do not pass the diagnostics gate. One official log drain adds $0.0822/hour (about $60/month), making the Supabase-billed full-month equivalent about **$190** before variable and external costs. Drain events are usage-variable at $0.20 per million-event package; egress and the external sink's storage/retention are additional. Thus the native-drain path is approximately $190/month plus variable usage, while an application telemetry alternative is acceptable only if separately proved to retain the required diagnostics and access controls ([log-drain pricing](https://supabase.com/docs/guides/platform/manage-your-usage/log-drains)). PITR, drains, and a 14-day sink do not themselves solve Proof-object recovery, deletion-tombstone replay, or 90-day application-domain audit; those remain application/runbook gates.

## Evidence still required before any backend decision

Vendor documentation narrows the design space but does not satisfy readiness. Each candidate still needs a small, representative spike or rehearsal that records:

1. Physical-device iOS and Android flows for two-photo Proof upload, interruption/resume, retry, duplicate submission, offline drafts, and acknowledgement only after durable object storage plus authoritative state.
2. Cross-Group and cross-role denial tests at the real authorization layer, including revoked membership and stale tokens.
3. Measured latency from intended pilot geographies and the consequences of the chosen data region.
4. A backup/restore drill showing structured-data RPO at most 15 minutes, core RTO at most four hours, recovered object/record reconciliation, deletion-tombstone replay, and no reappearance of deleted Proof.
5. A clock-controlled account deletion across active data, Auth, object versions/replicas, queues, exports, logs, and processor copies within the seven- and 30-day gates.
6. Correlated alerts and audit evidence with five-minute synthetic checks, human alert delivery within 15 minutes, 14-day diagnostic retention, 90-day restricted audit retention, and seven-day pseudonymization.
7. A cost model using the pilot's expected members, reads/writes, realtime listeners, two-photo volume, egress, function/task invocations, logs, backups, and any multi-region resources.
