# PWA authentication, session, and private-distribution constraints

Research snapshot: 2026-09-08. Sources are current official Supabase, PostgreSQL, MDN, Google Search, and OWASP documentation. This note applies the accepted email-OTP, PostgreSQL-authority, and Supabase Storage decisions to a browser-installed PWA. It does not provision hosting or change product policy.

## Decision-relevant conclusion

The PWA can preserve invitation-gated email OTP, immediate application access cutoffs, multiple-device sessions, private Proof media, and supported-browser deletion, but it should not transplant the native client's token-storage design into browser `localStorage`. Use a same-origin web backend/BFF that completes Supabase Auth exchanges and keeps refresh credentials in `HttpOnly; Secure; SameSite` host-only cookies. Browser JavaScript receives no refresh token and no privileged Supabase key. The backend verifies the session, checks current PostgreSQL Account and membership authority for every protected operation, and issues narrowly scoped, short-lived private Storage transfers only after that check.

This changes delivery topology, not authority: Supabase Auth still establishes identity; PostgreSQL remains authoritative for invitation, membership, revocation, deletion, and media eligibility; Supabase Storage remains the private object store.

## Constraint matrix

| Area | Current platform fact | Required PWA boundary |
| --- | --- | --- |
| Email OTP | Supabase supports email OTP through `signInWithOtp`/`verifyOtp`; OTP verification returns a session. Redirect URLs are allow-listed. Email links can be consumed by mail scanners, while typed OTP avoids link-prefetch acceptance ([passwordless email](https://supabase.com/docs/guides/auth/auth-email-passwordless), [email templates](https://supabase.com/docs/guides/auth/auth-email-templates)). | Keep six-digit typed OTP. A public request endpoint may reveal neither Account nor invitation existence. Rate-limit and return one neutral response. Server must reject unknown/uninvited identities before Auth-user creation and must atomically re-check the application invitation when membership is accepted. No GET or link preview performs acceptance. |
| Invitation gate | Supabase's Before User Created hook can deny creation using a Postgres function and is available on Free and Pro plans. Auth hooks run inside the Auth creation flow, but an Auth identity still does not encode Group capacity, expiry, revocation, or one-use semantics ([Before User Created hook](https://supabase.com/docs/guides/auth/auth-hooks/before-user-created-hook)). | Use the hook or a server-controlled provisioning path to ensure ordinary OTP cannot create unknown users. Keep the seven-day Group invitation as a separate digest-only application record and consume it only in the existing atomic acceptance command. Do not place the invitation secret in browser storage, logs, history-dependent analytics, or a service-worker cache. |
| OTP abuse | Supabase applies Auth endpoint limits; documented defaults include a 60-second resend window and project/IP quotas. CAPTCHA is supported but requires frontend/provider integration ([rate limits](https://supabase.com/docs/guides/auth/rate-limits), [CAPTCHA](https://supabase.com/docs/guides/auth/auth-captcha)). | Configure and test neutral throttling before pilot. Add CAPTCHA only if observed abuse requires it; doing so adds a third-party/privacy decision. Never let differing status, timing, or message text enumerate invited email addresses. |
| Browser session storage | Supabase sessions use short-lived JWT access tokens plus rotating single-use refresh tokens. Default sessions are indefinite and multi-device; access JWTs survive session revocation until expiry. Supabase permits custom storage and documents cookies for shared browser/server sessions ([sessions](https://supabase.com/docs/guides/auth/sessions), [server-side Auth](https://supabase.com/docs/guides/auth/server-side/advanced-guide)). OWASP advises against storing session identifiers, JWTs, or refresh tokens in Web Storage because any same-origin JavaScript can read them ([HTML5 security](https://cheatsheetseries.owasp.org/cheatsheets/HTML5_Security_Cheat_Sheet.html), [session management](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html)). | Prefer same-origin BFF-managed `__Host-` cookies with `HttpOnly`, `Secure`, `Path=/`, and `SameSite=Strict` where the OTP flow permits it. If redirect mechanics require `Lax`, document that exception. Never persist Auth tokens in `localStorage`, IndexedDB, Cache Storage, OPFS, or service-worker state. Rotate cookie contents on Supabase refresh and send auth responses with `Cache-Control: no-store`. |
| Multiple devices and revocation | Supabase supports `local`, `others`, and `global` sign-out. Revoking refresh tokens does not invalidate an already-issued access JWT before `exp`; configured session limits take effect on refresh ([signing out](https://supabase.com/docs/guides/auth/signout), [sessions](https://supabase.com/docs/guides/auth/sessions)). | Preserve multiple-device sessions. Expose explicit current-device and all-device sign-out semantics. Every protected command/read/media grant checks live Account, membership, access-cutoff, and—where immediate global sign-out is promised—session/cutoff state. Cookie deletion is client cleanup, never authoritative revocation. |
| CSRF | Cookies are attached by browsers, so cookie-authenticated mutations need CSRF defense. OWASP recommends no state-changing GETs, framework CSRF protection or a session-bound token in a custom header, Origin/Referer verification, and SameSite only as defense in depth ([CSRF prevention](https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html)). | All mutations use POST/PUT/PATCH/DELETE; verify exact allowed `Origin`; require a session-bound CSRF token/custom header; reject cross-site Fetch Metadata where available; keep CORS exact-origin and credentialed only where required. Reauthenticate destructive commands per existing contract. OTP login and invitation acceptance receive the same protection against login/client-side CSRF. |
| XSS | `HttpOnly` prevents JavaScript from reading cookies but XSS can still act as the user. MDN recommends output encoding/sanitization plus a nonce- or hash-based strict CSP; Trusted Types can constrain DOM injection sinks where supported ([XSS](https://developer.mozilla.org/en-US/docs/Web/Security/Attacks/XSS), [CSP](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/CSP)). | Render descriptions as text, never HTML; avoid `innerHTML`, `eval`, inline handlers, and unreviewed third-party scripts. Ship strict CSP, `object-src 'none'`, `base-uri 'none'`, `frame-ancestors 'none'`, restrictive `connect-src`/`img-src`, and Trusted Types where supported. Keep secrets/tokens out of URLs, telemetry, DOM, source maps, and logs. Treat dependency/script changes as security-sensitive. |
| Proof upload | Private Storage buckets are RLS-controlled by default. Supabase supports browser upload using a token from `createSignedUploadUrl`; overwrite is controlled when the signed URL is created ([private buckets](https://supabase.com/docs/guides/storage/buckets/fundamentals), [`uploadToSignedUrl`](https://supabase.com/docs/reference/javascript/file-buckets-uploadtosignedurl)). | Backend reserves one opaque immutable object key only after live session/membership/session-state checks, then returns a short-lived single-purpose upload token. Enforce bucket MIME/size limits, no upsert, one finalization command, and abandoned-upload cleanup. Keep selected pre-submission Proof device-private; service worker must not copy it into general caches. |
| Proof download and revocation | Private objects can use authenticated reads or time-limited signed URLs. Signed download URLs remain valid until expiry despite Auth-key rotation and cannot be individually revoked without provider support ([serving downloads](https://supabase.com/docs/guides/storage/serving/downloads)). | Mint a per-object short-lived read only after live authorization; five minutes remains the existing maximum. Send media/app responses with private/no-store or tightly bounded cache directives; never service-worker-cache Proof. Visibility cutoff stops new grants synchronously. Object quarantine/deletion, not Auth sign-out, handles already-issued URL revocation within the documented residual window. |
| Private HTTPS distribution | HTTPS is mandatory for secure cookies, service workers, and `Clear-Site-Data`. Search exclusion is not access control: Google says `robots.txt` can still leave URLs indexed; login protection and `noindex` are the relevant controls ([Clear-Site-Data](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Clear-Site-Data), [Google `noindex`](https://developers.google.com/search/docs/crawling-indexing/block-indexing), [robots.txt](https://developers.google.com/search/docs/crawling-indexing/robots/intro)). | Public shell contains no Group/member data. Require auth for every private route/API/object. Serve `X-Robots-Tag: noindex, nofollow, noarchive` (plus HTML meta fallback), publish no sitemap/private metadata, and optionally disallow crawling as noise reduction only. Use exact production/staging Auth redirect allow lists; isolate staging on another origin with separate credentials/data. |
| Browser-data deletion | `Clear-Site-Data` can request removal of cookies, cache, and storage, including IndexedDB and service-worker registrations, but MDN marks some directive support as variable. Browser storage is origin-scoped and can also be cleared/evicted independently ([Clear-Site-Data](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Clear-Site-Data)). | On sign-out/account deletion, first complete authoritative server revocation, then explicitly delete app IndexedDB/Cache Storage/OPFS data, unregister service workers where appropriate, clear in-memory state, and return `Clear-Site-Data: "cache", "cookies", "storage"` on a dedicated same-origin completion route. Verify each supported browser; if a browser cannot prove purge, block storing Proof/offline private data there rather than claim deletion. Server-side Account/Proof deletion remains separate and authoritative. |

## Service-worker and cache rules

- Precache only immutable public shell assets. Never cache OTP/auth responses, invitation URLs, authenticated API responses, signed Proof URLs, Proof bytes, member descriptions, or user-specific HTML.
- Network-only routes: Auth callbacks/OTP, invitation acceptance, all mutations, private media, Account deletion, and logout completion.
- Any offline structured snapshot needs its own minimized schema, expiry, membership-era key, explicit purge triggers, and supported-browser deletion tests. Treat it as untrusted display cache; never use it for authorization or final state.
- A service-worker update or stale tab must not keep access after departure/revocation. Protected online reads remain network-authorized; offline UI must lock/hide private cache when its bounded lease expires or revocation is observed.

## Required acceptance evidence

1. Typed OTP on every supported browser: invited, unknown, expired/revoked/consumed invitation, resend throttle, neutral enumeration behavior, scanner/prefetch GET, and concurrent acceptance.
2. Session matrix across installed/tab mode and multiple devices: refresh rotation, restart, current-device sign-out, other-device/global sign-out, Account cutoff, departed/removed member, stale tab, offline return, and still-unexpired JWT.
3. CSRF/XSS suite: cross-origin forms/fetches, missing/mismatched Origin and CSRF token, state-changing GET audit, stored descriptions, CSP enforcement/reporting, dependency scan, and absence of tokens/secrets from browser storage/logs/URLs.
4. Proof transfer matrix: unauthorized mint, expired token/URL, duplicate upload, wrong MIME/size/path, no-upsert, finalize race, membership cutoff between mint/finalize, cache inspection, and post-quarantine/delete retrieval.
5. Private-distribution checks: anonymous crawl receives no private content, all private responses are `noindex`/non-cacheable, redirect allow-list rejects foreign/staging origins, and no sitemap/manifest metadata exposes people or Groups.
6. Client purge on every supported browser in installed and tab modes: IndexedDB, Cache Storage, OPFS/file handles, service workers, cookies, history-safe URLs, open tabs, and offline relaunch. Separately rehearse server Account/Proof deletion and prove stale sessions cannot regain access.

## Decisions exposed for later tickets

- Select the concrete same-origin web framework/hosting topology that can own BFF cookies, Auth refresh, CSP nonces/hashes, exact-origin CSRF enforcement, and server-issued Storage grants without new provisioning yet.
- Define minimized offline private-data schema, lease duration, purge state machine, and unsupported-browser fallback. This cannot be delegated to generic service-worker caching.
- Decide whether CAPTCHA becomes pilot baseline only after threat/reliability testing; it adds provider, accessibility, and privacy consequences.
- Reconcile ADR 0003's native-only “platform secure storage” wording and direct-client media wording with the BFF/cookie PWA boundary while retaining email OTP and live PostgreSQL authority.

## Residual risk

Browser compromise, malicious extensions, and same-origin XSS cannot be made equivalent to native secure storage. HttpOnly cookies reduce token theft but do not stop an executing attacker from issuing authorized requests. Browser-side erasure also cannot guarantee deletion from device backups or a hostile/compromised client. Pilot claims must therefore be limited to tested supported-browser purge plus authoritative server deletion, backed by short-lived access, no Proof caching, strict XSS controls, and immediate live database cutoffs.
