# Supabase identity, authorization, and Group-isolation constraints

Research snapshot: 2026-09-01; the highest-risk Supabase Auth, session, RLS, API-key, MFA, invitation, and deletion claims were rechecked against the live official documentation on 2026-09-02. This note records decision-relevant constraints from current official Supabase, PostgreSQL, and Expo documentation. It does not choose the product's sign-in experience or add implementation scope.

## React Native sign-in, recovery, and session choices

Supabase Auth supports password, magic-link, one-time-password (OTP), social, phone, and SSO identities. The documented Expo/React Native client uses a public project URL and publishable key, persists the session through a storage adapter, enables automatic token refresh, and disables browser-style URL-session detection; Supabase also publishes an Expo social-auth example that uses Expo SecureStore on mobile. The publishable key is intended for public mobile clients, but it is safe only when database grants and Row Level Security (RLS) are correct ([Supabase Auth](https://supabase.com/docs/guides/auth), [Expo React Native quickstart](https://supabase.com/docs/guides/getting-started/quickstarts/expo-react-native), [Expo social-auth quickstart](https://supabase.com/docs/guides/auth/quickstarts/with-expo-react-native-social-auth), [API keys](https://supabase.com/docs/guides/getting-started/api-keys)).

The practical sign-in shapes are:

| Shape | Documented behavior and constraint |
| --- | --- |
| Email and password | `signInWithPassword` works directly in the React Native client. Recovery is a two-stage flow: `resetPasswordForEmail` sends a link to an allowed redirect, then the authenticated recovery screen calls `updateUser` with the new password. Hosted projects require email verification by default ([password-based Auth](https://supabase.com/docs/guides/auth/passwords)). |
| Email magic link or OTP | Supabase supports both. A magic link must return through a configured mobile link; an OTP can be entered in-app and verified with `verifyOtp`. Email-provider link prefetching can consume a one-click link, for which Supabase documents OTP or an intermediate confirmation page as mitigations ([email templates and prefetching](https://supabase.com/docs/guides/auth/auth-email-templates)). |
| Apple or Google | Supabase documents native/Expo social sign-in. Browser-based OAuth needs a redirect back to the app; provider tokens are not refreshed or stored by Supabase, so any provider API access would add a separate secure-token responsibility ([Expo social auth](https://supabase.com/docs/guides/auth/quickstarts/with-expo-react-native-social-auth), [social login](https://supabase.com/docs/guides/auth/social-login)). |

Confirmation, magic-link, recovery, invite, and OAuth flows can all redirect into the native app. Supabase requires a registered app scheme and an allow-listed redirect; Expo says stable authentication redirects should be tested in a development build with a custom scheme rather than Expo Go. Expo also recommends authorization code plus PKCE over implicit OAuth for public mobile clients ([Supabase native deep linking](https://supabase.com/docs/guides/auth/native-mobile-deep-linking), [Expo linking](https://docs.expo.dev/linking/into-other-apps/), [Expo authentication](https://docs.expo.dev/guides/authentication/)).

Expo SecureStore encrypts Android values with Android Keystore-backed storage and uses iOS Keychain services. Android values are removed on uninstall; iOS Keychain values may survive uninstall/reinstall with the same bundle ID, and values protected by `requireAuthentication` can become unreadable after biometric changes. SecureStore therefore needs an explicit sign-out/removal path and cannot be treated as an authoritative account or session record ([Expo SecureStore](https://docs.expo.dev/versions/latest/sdk/securestore/)).

A Supabase session consists of a short-lived JWT access token plus a single-use rotating refresh token. By default, sessions have no fixed lifetime and a user may have multiple active sessions; paid plans can add time-box, inactivity, or single-session controls. Supabase generally recommends the default one-hour JWT lifetime and warns against values below five minutes. Ending a database session prevents future refresh, but a previously issued stateless JWT can remain usable until its `exp` time unless a sensitive operation also confirms that its `session_id` still exists ([user sessions](https://supabase.com/docs/guides/auth/sessions)).

## JWT and custom-claim boundaries

The access token's `sub` claim is the stable Supabase Auth user identifier, `role` selects the Postgres role used by RLS, `aal` records authentication assurance, and `session_id` identifies the Auth session. Server code should verify Supabase JWTs with `getClaims()` or a maintained JWT library rather than implement signature verification itself; `getSession()` reads local session storage and its embedded user object is not an authorization proof ([Supabase JWTs](https://supabase.com/docs/guides/auth/jwts), [`getClaims`](https://supabase.com/docs/reference/javascript/auth-getclaims), [server client guidance](https://supabase.com/docs/guides/auth/server-side/creating-a-client)).

`user_metadata` is writable by the authenticated user and must not carry authorization facts. `app_metadata` is not user-writable and may carry authorization data, but JWT contents remain stale until the token is refreshed; Supabase specifically cautions that removing a user from a team is not reflected in `auth.jwt()` until refresh. A Custom Access Token Hook can add claims before token issuance, but it does not make mutable membership current between issues of the token ([RLS `auth.jwt()` guidance](https://supabase.com/docs/guides/database/postgres/row-level-security), [Custom Access Token Hook](https://supabase.com/docs/guides/auth/auth-hooks/custom-access-token-hook)).

**Decision implication:** use `sub` only to identify the caller, and resolve current Group membership, Group-admin status, departure, suspension, and membership-era visibility from authoritative application tables on each protected operation. Do not put a Group ID, current membership, or Group role in `user_metadata`; do not make a custom JWT claim the sole authorization check for facts that require immediate revocation. A coarse, slow-changing claim may help presentation or routing, but the database or application API must re-check live authority before acting ([RLS and stale JWTs](https://supabase.com/docs/guides/database/postgres/row-level-security)).

## Group isolation with PostgreSQL RLS

PostgreSQL RLS limits which rows a role may select, insert, update, or delete. Once RLS is enabled, the absence of an applicable policy is default-deny. `USING` controls existing rows visible to an operation, while `WITH CHECK` controls rows introduced by `INSERT` or the new version produced by `UPDATE`. Multiple permissive policies combine with `OR`, so broad convenience policies can unintentionally widen access ([PostgreSQL row security](https://www.postgresql.org/docs/current/ddl-rowsecurity.html), [`CREATE POLICY`](https://www.postgresql.org/docs/current/sql-createpolicy.html)).

RLS is not a replacement for object privileges: exposed tables need least-privilege grants as well as RLS. Supabase advises enabling RLS for every table or view exposed through the Data API and granting only required operations. Table owners, superusers, and roles with `BYPASSRLS` normally bypass policies; referential-integrity checks also bypass RLS, so constraint errors can become an inference channel and should not be returned raw across a tenant boundary ([Supabase API security](https://supabase.com/docs/guides/api/securing-your-api), [PostgreSQL row security](https://www.postgresql.org/docs/current/ddl-rowsecurity.html)).

**Decision implication:** every Group-owned application row and private Storage object should have an authoritative Group association, and every user-facing read or write should prove a live membership row for `auth.uid()` in that same Group. Command-specific policies should separately express read visibility, permissible mutation of existing rows, and permitted new `group_id`/owner values. Membership-era rules require timestamps or immutable membership identifiers in the policy predicate rather than a current-membership boolean alone. PostgreSQL can enforce "one active Group per person" with a unique partial index over active membership rows, while capacity and last-admin rules need transactional command logic because they depend on multiple rows ([partial unique indexes](https://www.postgresql.org/docs/current/indexes-partial.html), [RLS policy semantics](https://www.postgresql.org/docs/current/sql-createpolicy.html)).

Views and functions need their own boundaries. Supabase warns that views created by the project owner bypass underlying RLS by default; use a `security_invoker` view where supported or keep the view out of exposed schemas. Functions are `SECURITY INVOKER` by default. A `SECURITY DEFINER` function runs with its owner's privileges and can bypass RLS when owned by a bypass role; PostgreSQL and Supabase require a trusted/pinned `search_path`, schema-qualified object names, revocation of default `PUBLIC` execution, and selective `EXECUTE` grants. Supabase additionally advises keeping such functions out of exposed schemas ([Supabase RLS views and definer functions](https://supabase.com/docs/guides/database/postgres/row-level-security), [Supabase database functions](https://supabase.com/docs/guides/database/functions), [PostgreSQL safe `SECURITY DEFINER`](https://www.postgresql.org/docs/current/sql-createfunction.html)).

**Decision implication:** keep ordinary authorization in invoker-context RLS. Reserve definer functions for narrow atomic operations that cannot be expressed safely otherwise; place them in a private schema, set `search_path = ''`, schema-qualify every object, revoke `PUBLIC`, grant only the calling backend role, derive the actor from verified Auth context, and re-check membership/role inside the function. Cross-Group denial tests must cover every command, view, function, Storage path, departed/rejoined member, Group admin, and operator path because a definer or bypass-key call will not be rescued by RLS ([Supabase RLS testing and definer guidance](https://supabase.com/docs/guides/database/postgres/row-level-security), [PostgreSQL function security](https://www.postgresql.org/docs/current/perm-functions.html)).

## Privileged keys and operator/admin boundaries

The React Native bundle may contain only the publishable key. Supabase secret keys and legacy `service_role` keys provide the `service_role` Postgres role, bypass all RLS, and must exist only in developer-controlled backend components such as Edge Functions, workers, or a secured operator service. They must not be bundled in mobile binaries, URLs, logs, chat, or other public/client surfaces ([Supabase API keys](https://supabase.com/docs/guides/getting-started/api-keys), [secure data](https://supabase.com/docs/guides/database/secure-data)).

A privileged Supabase client should be separate from any user-session client. Supabase documents that a user session can replace the default `Authorization` header on a client initialized with a service key, changing whether RLS is bypassed. Conversely, a correctly privileged request skips RLS entirely, and adding `service_role` to an RLS policy has no effect ([service-role client behavior](https://supabase.com/docs/guides/troubleshooting/why-is-my-service-role-key-client-getting-rls-errors-or-not-returning-data-7_1K9z)).

**Decision implication:** privileged code must authenticate and authorize the caller before using the secret-key client, accept no client assertion of Group or operator authority without a live database check, expose only named use-case operations, and write restricted audit evidence for each operator action. Prefer user-scoped/invoker calls for normal member behavior; contain the bypass client to Auth administration, deletion orchestration, queue/maintenance work, and explicitly approved operator commands ([API-key permitted uses](https://supabase.com/docs/guides/getting-started/api-keys)).

## Invitation tokens and links

`auth.admin.inviteUserByEmail()` is a server-only Auth administration call. It creates an unconfirmed Auth user, sends the Auth invite template, and can attach a redirect URL and user metadata. The redirect must match the project's allow list; otherwise Supabase silently falls back to the Site URL. Auth invitation links expire according to the project-wide Email OTP expiration setting, documented as one hour by default ([Supabase users and invitations](https://supabase.com/docs/guides/auth/users)).

An Auth invite proves control of an email and establishes an Auth identity; it does not by itself encode the live capacity, revocation, one-use, one-Group, membership-era, or role rules of an application Group. If those Group semantics or expiry differ from the project-wide Auth-email setting, represent the Group invitation as a separate application record and make acceptance one atomic server-side transaction that locks/validates the invitation and Group, creates the membership, then marks the invitation consumed. This is an architectural inference from the documented Auth-invite scope and RLS/transaction boundary, not a Supabase product feature ([Auth invitations](https://supabase.com/docs/guides/auth/users), [PostgreSQL transaction isolation](https://www.postgresql.org/docs/current/transaction-iso.html)).

For a custom Group link, PostgreSQL `pgcrypto` can generate cryptographically strong random bytes and compute a digest. A bounded design can send the opaque value once, store only its digest with invite ID, Group ID, intended identity/email binding, expiry, revoked/consumed timestamps, and compare the digest during the atomic acceptance operation. Supabase's own email templates similarly expose a `TokenHash` for server-side verification, and document that email scanners may prefetch and consume one-click confirmation links; an explicit in-app confirmation step avoids treating a link-preview GET as Group acceptance ([PostgreSQL `pgcrypto`](https://www.postgresql.org/docs/current/pgcrypto.html), [Supabase email-template tokens and prefetching](https://supabase.com/docs/guides/auth/auth-email-templates)).

## MFA, reauthentication, and sensitive actions

Supabase MFA supports TOTP and phone factors. A conventional login produces `aal1`; successful challenge and verification of an additional factor produces `aal2`, which appears in the access token and can be required by restrictive RLS policies or checked in another verified API. Supabase documents optional, mandatory, and group-specific MFA experiences and recommends redirecting an `aal1` user to complete the enrolled factor rather than treating the state as a generic sign-out ([Supabase MFA](https://supabase.com/docs/guides/auth/auth-mfa), [TOTP flow](https://supabase.com/docs/guides/auth/auth-mfa/totp), [RLS MFA example](https://supabase.com/docs/guides/database/postgres/row-level-security)).

Supabase's `reauthenticate()` sends a nonce to a signed-in user's confirmed email or phone. With Secure Password Change enabled, a user whose session is older than 24 hours must supply that nonce to `updateUser` when changing a password. That documented nonce flow is specific to password change; it should not be assumed to protect arbitrary application commands ([password security](https://supabase.com/docs/guides/auth/password-security), [`reauthenticate`](https://supabase.com/docs/reference/javascript/auth-reauthenticate), [`updateUser`](https://supabase.com/docs/reference/javascript/auth-updateuser)).

**Decision implication:** define step-up per sensitive command, not only in the UI. At minimum, enforce verified `aal2` for privileged operator access when MFA is enabled and re-check `aal` at the server/RLS boundary. For destructive member actions such as account deletion, select and document a fresh-auth proof compatible with the chosen first factor; Supabase's password-change nonce cannot be reused as an undocumented general-purpose authorization token. Any bypass-key implementation must check the verified claim itself because RLS will not run ([MFA API guidance](https://supabase.com/docs/guides/auth/auth-mfa), [secret-key bypass](https://supabase.com/docs/guides/getting-started/api-keys)).

## Auth account deletion and administration

Auth Admin methods such as creating, updating, listing, inviting, and deleting users are server-only and require a secret or legacy service-role key. Admin updates apply directly and bypass the ordinary user confirmation flows, so they belong behind the rare, authenticated, authorized, and audited operator boundary rather than in the member client ([Auth Admin `createUser`](https://supabase.com/docs/reference/javascript/auth-admin-createuser), [`updateUserById`](https://supabase.com/docs/reference/javascript/auth-admin-updateuserbyid), [`listUsers`](https://supabase.com/docs/reference/javascript/auth-admin-listusers), [`deleteUser`](https://supabase.com/docs/reference/javascript/auth-admin-deleteuser)).

`auth.admin.deleteUser()` defaults to hard deletion. Its soft-delete option retains a non-reversible hashed identifier, so soft deletion is not equivalent to erasure. Hard deletion removes `auth.users`, cascades to `auth.sessions`, and prevents refresh-token use, but already-issued access JWTs remain valid until expiry unless sensitive APIs validate `session_id`. A temporary ban and an application-only deleted flag do not revoke existing sessions. Supabase also refuses Auth-user deletion while that user owns Storage objects; Storage objects must first be removed through the Storage API or ownership reassigned ([Auth user management and access removal](https://supabase.com/docs/guides/auth/managing-user-data), [`deleteUser`](https://supabase.com/docs/reference/javascript/auth-admin-deleteuser), [Storage object deletion](https://supabase.com/docs/guides/storage/management/delete-objects)).

**Decision implication:** account deletion must be an idempotent server-side workflow, not a single Auth call: immediately deny application access from live state; stop/clean dependent work; remove private Storage objects through the Storage API; delete or pseudonymize application rows under the project's retention rules; hard-delete the Auth user; and record completion/failures without tokens or sensitive payloads. During the outstanding-JWT window, all user-facing operations must consult the live disabled/deletion state or session existence so a deleted account cannot use a still-unexpired token ([Supabase account-access removal](https://supabase.com/docs/guides/auth/managing-user-data), [Supabase sessions](https://supabase.com/docs/guides/auth/sessions)).

## Evidence the eventual design still needs

Official documentation establishes mechanisms, not the correctness of this application's policies. Before pilot readiness, implementation evidence should include: physical-device sign-in/recovery/deep-link tests on iOS and Android; session persistence, sign-out, reinstall, expiry, and revoked-session cases; an RLS matrix with member, nonmember, departed, rejoined, admin, and operator cases; concurrent invitation acceptance/revocation/capacity tests; definer-function and exposed-view review; no privileged key in the client bundle or logs; `aal1`/`aal2` step-up tests; and a deletion rehearsal covering Storage, application data, Auth sessions, an outstanding JWT, retry, and audit completion. This test list follows the failure boundaries explicitly documented for deep links, SecureStore, RLS, bypass keys, MFA, sessions, and deletion above.
