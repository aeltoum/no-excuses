# PWA Proof capture and private offline storage

Research snapshot: 2026-09-08. Sources are current web standards, WebKit, Chrome, and project contracts. This note evaluates a pure PWA; it does not select tooling, provision services, or weaken existing Proof rules.

## Answer

A pure PWA can implement camera-only Proof capture and best-effort device-private drafts on current Safari, Chrome, and Edge, but it **cannot promise durable unattended upload or deadline-triggered deletion while closed across supported browsers**. The viable contract is: capture from an app-owned live `getUserMedia()` stream; re-encode and verify every image before local persistence/upload; keep an explicit local outbox; retry while open and opportunistically where Background Sync exists; tell the member when upload is not server-confirmed; expire and erase drafts on every wake/open; and treat browser/OS eviction as possible data loss. Submission must remain incomplete until the server durably acknowledges both selected images and the report.

This preserves live capture, explicit submission consent, no library import, no location/device metadata disclosure, and immediate server-side visibility revocation. It does **not** satisfy a literal promise that an unsubmitted device-only draft will be physically deleted at a deadline while the PWA never runs. Product language and acceptance evidence must define draft expiry as immediate denial and best-effort byte erasure on next execution, or the pilot needs a different design boundary. No browser API can attest physical erasure from browser profiles, device backups, or browser-managed storage.

## Capability and failure matrix

| Area | Supported-browser fact | Required design / failure behavior |
|---|---|---|
| Live camera-only capture | `getUserMedia()` obtains a permissioned live media-input stream in a secure context. Camera permission may be denied, hardware may be missing/busy, constraints may fail, or the user may ignore the prompt indefinitely. Required constraints such as an exact facing mode may reject on some devices; unsupported constraint names are silently ignored. ([Media Capture and Streams](https://www.w3.org/TR/mediacapture-streams/), [MDN `getUserMedia`](https://developer.mozilla.org/en-US/docs/Web/API/MediaDevices/getUserMedia)) | Use only `navigator.mediaDevices.getUserMedia({video: ...})` plus an app-rendered shutter capturing the current stream frame. Do not expose `<input type=file>`, drag/drop, paste, share-target, or File System Access import paths. Offer front/rear preference, not a hard rear-camera dependency; provide retry, settings help, and an accessible explanation when permission fails. Stop tracks immediately after capture/exit. |
| Provenance | `getUserMedia()` establishes a contemporaneous media-input stream, not identity, exercise completion, trustworthy clock, or unmodified sensor provenance. A media source may be physical or virtual, and the web platform does not provide tamper-proof capture attestation. ([Media Capture and Streams](https://www.w3.org/TR/mediacapture-streams/)) | “Captured through product camera during active Workout session” is enforceable as UI/data-flow provenance, not forensic proof. Record server session bounds and client capture time as claims; never market anti-spoofing. Keep peer review and member attestation authoritative. |
| Metadata | Browser capture/encoding behavior is not a privacy contract for EXIF, GPS, device model, filenames, or embedded profiles. Canvas export creates a newly encoded image, but standards do not promise the exact metadata policy of every encoder. ([HTML canvas `toBlob`](https://html.spec.whatwg.org/multipage/canvas.html#dom-canvas-toblob-dev)) | Decode, normalize orientation, resize, and re-encode in the client; then parse/allowlist the produced format before persistence. Repeat authoritative server-side decode/re-encode or metadata stripping and verify absence before publication. Never store original camera files, filenames, device labels, `MediaTrackSettings`, location, or EXIF. |
| IndexedDB and OPFS | IndexedDB is transactional origin storage; OPFS is an origin-private storage endpoint. Both live in the origin's browser-managed storage bucket, not a user-visible private vault. Default storage is `best-effort`; `navigator.storage.persist()` can request persistent mode, but grant policy is user-agent controlled. Users may clear even persistent data. ([Indexed Database API](https://w3c.github.io/IndexedDB/), [File System Standard](https://fs.spec.whatwg.org/), [Storage Standard](https://storage.spec.whatwg.org/)) | Prefer IndexedDB for state/indexes and OPFS only after runtime capability tests for large blobs; keep an IndexedDB blob fallback. Request persistence after meaningful user action, inspect `persisted()`, quota, and write results, but never equate `true` with backup or durability. Encrypt local Proof blobs with a non-exported app key where supported; XSS/same-origin code remains inside the trust boundary, so CSP, dependency control, and no third-party script are mandatory. |
| Safari retention | WebKit's seven-day cap applies to script-writable website storage after seven days without user interaction, but WebKit says installed Home Screen web apps are exempt. Users and storage pressure can still remove data. ([WebKit storage policy](https://webkit.org/blog/10218/full-third-party-cookie-blocking-and-more/)) | Require Home Screen installation on iPhone/iPad as already chosen for onboarding. Still label drafts “saved on this device, may be lost”; never count an unacknowledged draft as submitted. Test tab mode too, but do not promise draft survival there. |
| Offline recovery | Service workers, Cache Storage, IndexedDB, and OPFS can restore an app shell and outbox after ordinary reload/restart, subject to quota, eviction, corruption, browser clearing, app updates, and write failures. Service workers are event-driven and may be terminated when work is not tied to an event lifetime. ([Service Workers](https://w3c.github.io/ServiceWorker/), [Storage Standard](https://storage.spec.whatwg.org/)) | Commit draft metadata and each selected blob atomically enough to detect partial writes; checksum blobs; version migrations; maintain states `local`, `uploading`, `uploaded-unfinalized`, `submitted`; reconcile with server on every launch/focus/online event; retain local bytes until server acknowledgement or explicit deletion; expose recovery/export only if consistent with “no personal archive” (default: no export). |
| Durable upload | Background Sync is designed to retry outbox work, but its spec leaves retry timing to the browser. Chromium supports it; WebKit's implementation request remains open and its standards-position request has no adopted position. Without it, a closed Safari/Home Screen PWA waits for a later app execution. Even with it, no deadline or exactly-once guarantee exists. ([Background Sync specification](https://wicg.github.io/background-sync/spec/), [WebKit implementation bug](https://bugs.webkit.org/show_bug.cgi?id=201866), [WebKit position request](https://github.com/WebKit/standards-positions/issues/14), [Chrome Background Sync](https://developer.chrome.com/blog/background-sync)) | Baseline = foreground resumable upload with explicit progress and retry. Register one-off Background Sync only as enhancement. Use idempotent reserved object keys, checksums, server reconciliation, and a finalize command after both objects exist. Warn before close/navigation and show persistent “Not submitted—reopen to finish” status. Never claim upload will finish while closed. |
| Consent and publication | Local storage does not itself share media. Network upload does. Project contract requires selected images remain member-private until explicit submission and current plain-language media-sharing consent; submission publishes only after required review flow. ([Proof photo contract](../../CONTEXT.md#proof-photo)) | Local capture and draft storage precede sharing consent only if onboarding language clearly covers device-local processing. Obtain current submission consent immediately before finalize. Upload, if performed before that click, must land in an author-only, non-publishable staging state with automatic deletion; safer baseline is upload after consent. Server rechecks consent and membership atomically at finalize. |
| Deletion | Web APIs allow logical deletion from IndexedDB/OPFS when code executes, but provide no physical-erasure receipt and cannot schedule arbitrary code at an exact future deadline. Browser-profile clearing/eviction may delete earlier; device/browser backup behavior is outside the app's control. | Explicit member deletion while open: revoke UI access, delete local records/blobs, clear thumbnails/object URLs, then verify lookup failure. Deadline/membership termination: server revokes and deletes any uploaded staging bytes on schedule; client marks server-reported tombstones and erases local copies on next execution. Document that device-only bytes cannot be proven erased while app never runs. This is the only identified mismatch with a literal exact local-deletion promise. |

## Privacy, consent, accessibility, and deletion verdict

- **Satisfiable:** camera permission and clear purpose before activation; live-stream-only UI; no library picker; two member-selected photos; local privacy before submission; current consent at submission; no location/device metadata disclosed; synchronous server access revocation; server media deletion periods; member participation without later push permission.
- **Satisfiable only with explicit engineering controls:** client and server re-encoding/metadata verification; same-origin script supply-chain boundary; storage corruption/eviction recovery; author-only staging; idempotent upload/finalize; no caching of private responses by service worker; accessible permission-denial, offline, upload-progress, and recovery states; physical-device testing across every supported client and assistive technology.
- **Not literally satisfiable by pure PWA:** guaranteed survival of a device-only draft; guaranteed closed-app upload by a deadline; exact timed deletion of local bytes while the PWA never executes; proof or attestation of physical deletion from browser storage/device backups. These limitations are not repaired by OPFS, persistent storage, service workers, or Background Sync.

## Recommended contract decisions

1. Keep “camera-only” and define it as frames captured from an app-owned `getUserMedia()` session; prohibit all file/library ingress.
2. Make local draft persistence explicitly **best effort**. A server-confirmed submission, never a queued local action, is the accountability event.
3. Require foreground completion on Safari. Background Sync may improve Chromium behavior but cannot be part of acceptance semantics.
4. Define cutoff behavior: after cutoff, the server rejects finalize; next client execution immediately tombstones and erases the draft. If policy requires byte deletion at cutoff even when the device stays offline/closed, reject pure PWA for offline photo drafts or avoid persisting photo bytes locally.
5. Treat IndexedDB as required baseline; OPFS as capability-gated optimization. Do not split product semantics by storage API.
6. Create physical-device acceptance tests for iPhone/iPad Home Screen Safari, Android Chrome, desktop Safari/Chrome/Edge covering permission denial/non-response, camera switch, interruption/backgrounding, storage denied/full/evicted, crash between blob and index writes, offline restart, duplicate upload, expired consent, cutoff during upload, metadata fixtures, screen reader, zoom/reflow, reduced motion, and keyboard operation.

## Newly sharp decisions

- Decide whether “unsubmitted draft deletes when its reporting cutoff passes” means server/UI inaccessibility plus client erasure on next execution, or strict device-byte deletion at the instant of cutoff. Strict instant deletion rules out persistent offline Proof bytes in a pure PWA.
- Decide whether pre-submit author-only staging is allowed. If not, offline-captured images cannot start upload until the member gives submission consent, increasing foreground completion risk.
- Decide maximum encoded dimensions/bytes and the upload-resume protocol, based on physical-device capture and interruption testing rather than framework defaults.
